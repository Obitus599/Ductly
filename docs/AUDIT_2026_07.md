# Audit remediation — July 2026

Every finding from the 2026-07 codebase audit, and what was done about it.
Severity is the audit's. "Verified" says how the fix was proven, not just
that code was written.

---

## Critical

### C1 — Tabby webhook confirmed bookings on the request body alone
`src/app/api/webhooks/tabby/route.ts`

The handler read `payload.status`; on `"closed"` it skipped both
`capturePayment` and `retrievePayment` and went straight to
`confirmPaidBooking`. Auth was `if (secret) { ... }`, so an unset
`TABBY_WEBHOOK_SECRET` disabled authentication entirely, and the comparison
was a plain `!==`.

**Fixed:** auth fails closed (missing secret → 500, like the Stripe
webhook), constant-time compare, `Authorization: Bearer <secret>` accepted.
The body is now used only to *locate* the payment — the authoritative
status always comes from a server-to-server `retrievePayment`, for every
branch including `expired`/`rejected`. An unverifiable status returns 503
so Tabby retries rather than the notification being silently dropped.

**Verified:** `src/__tests__/api/tabby-webhook.test.ts` — including
"does NOT confirm when the body claims closed but Tabby says CREATED" and
"does NOT expire when the body says expired but Tabby says AUTHORIZED".

### C2 — `booking_locks` capacity check was check-then-insert
`supabase/schema.sql`, new migration `20260727000000`

The trigger counted existing holds, then the row was inserted, with
nothing serialising the two steps. Two customers racing for the last free
slot both read "0 used" and both won — one ends up confirmed, charged, and
with no team able to serve them.

**Fixed:** `pg_advisory_xact_lock`, keyed on the slot's epoch seconds, at
the top of `check_booking_lock_limit()`. Same-slot inserts queue; different
slots stay fully parallel.

**Verified empirically** against Postgres 17 — 12 concurrent inserts for
one slot with capacity 1:

| trigger | holds granted (3 runs) |
| --- | --- |
| pre-fix | 2, 1, 8 |
| with advisory lock | 1, 1, 1 |

### C3 — a payment that landed after the stale sweep lost the money
`src/lib/booking-confirmation.ts`, `src/lib/maintenance.ts`

The sweep flipped `pending → expired` after 15 minutes. A slow-but-
successful hosted checkout could land on the wrong side of that, and the
confirm CAS only accepted `pending`/`payment_failed` — so it matched 0
rows: no confirm, no dispatch, no refund, and the return value was ignored.

**Fixed:** `expired` added to the CAS (every caller has already verified
the money server-side, so refusing here loses the booking while keeping the
charge). The TTL moved to `lib/maintenance` and rose 15 → 45 minutes, above
the slowest realistic checkout. A genuinely unconfirmable booking
(cancelled/completed) now writes a `confirm_not_confirmable` /
`REFUND REQUIRED` row to `error_log` instead of returning silently.

**Verified:** `src/__tests__/lib/booking-confirmation.test.ts`.

## High

### H1 — `status: "failed"` violated the DB CHECK constraint (×4)
`src/app/api/checkout/route.ts` (was lines 284, 317, 330, 442)

`bookings_status_check` allows `payment_failed`, not `failed`. All four
updates were rejected with `23514`, and because the error was unchecked the
booking silently stayed `pending`, holding its slot until the sweep.

**Fixed:** a single `abandonBooking()` helper writing `payment_failed`,
guarded on `status = 'pending'`, with the error surfaced to `error_log`.

**Verified:** reproduced the exact rejection on Postgres 17 —
`UPDATE bookings SET status='failed'` → `ERROR: new row for relation
"bookings" violates check constraint "bookings_status_check"`, while all
eight statuses the app writes are accepted.

### H2 — Tabby callback showed a false success page during a Tabby outage
`src/app/api/tabby/callback/route.ts`, new `src/app/book/pending/page.tsx`

When `retrievePayment` failed, `st` was undefined, no branch matched, and
control fell through to `if (result === "success")` — which defaults to
`"success"`. The customer saw "Booking Confirmed" for a `pending` booking
with an uncaptured payment.

**Fixed:** `/book/success` is reachable only when we positively confirmed
the booking ourselves (or it was already `confirmed`). Every other path —
outage, non-terminal payment, missing payment id — lands on a neutral
`/book/pending` page that polls until the webhook settles it.

**Verified:** `src/__tests__/api/tabby-callback.test.ts`, "never shows
success for an unconfirmed booking" (5 cases).

### H3 — one team could be assigned two overlapping jobs
`supabase/schema.sql`, `src/lib/scheduling-agent.ts`

`UNIQUE(team_id, slot_start)` only catches jobs starting at the same
instant. 10:00–11:30 and 10:30–12:00 for one team collide in reality but
not in that constraint, and `deterministicAssign` compared `slot_start` for
exact equality when deciding who was free.

**Fixed:** `slot_locks` gained `slot_end` (backfilled from the booking) and
a GiST exclusion constraint
`EXCLUDE (team_id WITH =, tstzrange(slot_start, slot_end, '[)') WITH &&)`,
plus a `slot_end > slot_start` check so an empty range can't quietly
disable it. The agent now excludes teams with an overlapping lock *or*
booking, reads the window from the booking row (never from the LLM's tool
arguments), and walks down the ranked list if the constraint rejects its
first pick.

**Verified:** constraint behaviour tested on Postgres 17 — overlap
rejected, same window for a different team accepted, back-to-back
(touching) accepted, inverted range rejected. Migration also de-duplicates
pre-existing overlapping rows; tested against a seeded dirty database.
App-side: `src/lib/scheduling-agent.test.ts`.

### H4 — admin booking creation had a weaker slot guard than checkout
`src/app/api/admin/bookings/create/route.ts`

Three independent gaps: `booking_locks` were ignored, unassigned pending
bookings were skipped (`if (!b.team_id) continue`), and occupancy and
blackouts were tallied separately — so 1 team busy + the other blacked out
read as "1 of 2" twice.

**Fixed:** one combined consumed-capacity number over occupied teams,
blacked-out teams and active holds.

**Verified:** three new cases in
`src/__tests__/api/admin-bookings-create.test.ts`.

### H5 — PDPL erasure left the customer fully identifiable
`src/app/api/me/delete/route.ts`

Anonymising `customers` left raw name/email/phone in
`contact_submissions`, `feedback`, `verification_codes` and `error_log`.

**Fixed:** each is now swept (anonymise or delete as appropriate), each
independently, so one failure doesn't skip the rest. A partial erasure
returns `residual_tables` and logs `pdpl_erasure_incomplete` instead of
claiming success.

**Verified:** `src/__tests__/api/me-delete.test.ts`, including the
partial-failure path.

## New operational requirements

- **`CRON_SECRET`** — required for `POST /api/cron/cleanup`; unset means the
  endpoint is disabled (503), not open. Schedule it every ~10 minutes:
  ```
  curl -X POST -H "Authorization: Bearer $CRON_SECRET" https://ductly.ae/api/cron/cleanup
  ```
- **`TABBY_WEBHOOK_SECRET`** — now mandatory once Tabby is configured.
  `validateEnv()` refuses to boot without it, because the webhook fails
  closed and a half-configured install would silently stop confirming BNPL
  bookings.
- **`TRUSTED_PROXY_HOPS`** — defaults to 1 (a single nginx/Plesk in front of
  `next start`). Raise it if a CDN is added, or client IPs will be read from
  the wrong position in the chain.
- **Migration `20260727000000`** needs the `btree_gist` extension. It is
  idempotent and de-duplicates pre-existing overlapping `slot_locks` rows
  before adding the exclusion constraint.
